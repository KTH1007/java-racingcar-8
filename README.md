## 기능 목록

### 1. 입력 기능
- 사용자에게 자동차 이름을 문자열로 입력 받음 (","를 기준으로 입력 받음)
- 받아온 자동차 이름을 ","로 구분하여 분리

### 2. 자동차 도메인
- 사용자가 입력한 자동차의 이름 길이가 5자 이하인지 체크
- 자동차의 이름과 총 몇 칸 이동했는지 표시
- 자동차의 입력을 받았을 때 총 이동 칸 수는 0으로 초기화

### 3. 자동차 이름 추출 도메인
- null/공백 체크
- 구분자 처리
- 중복된 이름 검증

### 4. 실행 횟수를 관리할 도메인
- 이동할 횟수를 입력 받을 때 음수나 소수점이 들어오지 않는지 체크

### 5. 무작위 값을 위한 랜덤 도메인
- 0 ~ 9까지의 값을 랜덤으로 가져와 값이 4이상인 경우 해당 자동차를 전진

### 6. 순위를 위한 서비스 로직
- 반복문을 이용해 자동차들의 이동 칸 수중 max 값을 구함
- max을 값과 이동 칸 수가 같은 자동차를 List에 저장

### 7. 출력 기능
- 자동차 이름을 입력 받기 위한 메시지 출력 -> "경주할 자동차 이름을 입력하세요.(이름은 쉼표(,) 기준으로 구분)"
- 시도할 횟수를 입력 받기 위한 메시지 출력 -> "시도할 횟수는 몇 회인가요?"
- List에 담겨진 우승자를 아래에 맞게 출력
  - 시도 횟수에 맞게 몇 칸 이동했는지 "-"로 표시 (ex: pobi : --)
  - 단독 우승자인 경우 메시지 출력 "최종 우승자 : pobi"
  - 공동 우승자가 있는 경우 메시지 출력 "최종 우승자 : pobi, jun"

### 8. 전체 흐름 통합
- Application.main()에서 전체 프로세스 실행

### 9. 테스트 케이스 작성
- 도메인별 단위 테스트 진행
- 통합 테스트 진행

## 고민한 점 및 생각

### 1. 도메인 분류
처음에는 단순히 자동차를 움직이는 것이기 때문에 자동차와 자동차를 분류해주는 도메인 2개만 필요하면 될 것 같았습니다.
하지만 자동차 도메인에서 자동차 컬렉션까지 관리를 하게 되었고 경주 횟수 검증 및 랜덤 로직 분류도 안 되고 있어서 도메인을 총 5개로 나누게 되었습니다.
- Car: 개별 자동차 관리
- Cars: 자동차 컬렉션 관리 (일급 컬렉션)
- NameExtractor: 이름 추출/검증 로직 분리
- RaceCount: 경주 횟수 검증/관리
- RandomNumberGenerator: 랜덤 로직 분리

사실 일급 컬렉션이라는 것은 1주차 공통 피드백을 보고 처음 알게되었습니다.
그래서 이게 정확히 무엇이고 왜 사용해야 되는건지에 대해 알아버게 되었습니다.
제가 나름대로 찾아보면서 정리한 것은 아래와 같습니다.

- 비즈니스 로직 캡술화로 인해 비즈니스 로직이 외부에 노출되지 않음
- 상태와 행위 등을 한 곳에서 관리
- 불변성 보장

위와 같은 기능들을 제공할 수 있기 때문에 아마 단순하게 데이터 전달을 하는 경우에는 안 써도 되겠다고 생각하였습니다.

### 2. getter 지양
공부를 하면서 setter를 지양하라는 얘기는 많이 들었지만 getter를 지양해야 한다는 말은 한 번도 듣지 못했습니다.
그래서 왜 getter를 지양해야 할까? 하는 의문이 생겼습니다.

많은 블로그를 찾아본 끝에 정답을 알 수 있었습니다.

- 캡슐화 위반
  - 객체의 내부 상태를 외부에 노출하여 정보 은닉 원칙을 깨뜨림
  - 객체가 가진 데이터에 직접 접근할 수 있게 되어 객체의 경계가 모호해짐

- 객체지향 설계 원칙 위배
  - "Tell, Don`t ASK(TDA)" 원칙 위반" 객체에게 데이터를 요청하는 대신 행동을 요청해야 함
  - 객체가 단순한 데이터 컨테이너로 전략할 위험

- 높은 결합도
  - 클라이언트 코드가 객체의 내부 구조에 의존하게 됨
  - 내부 구현 변경 시 클라이언트 코드로 함께 수정해야 하는 문제

이러한 문제가 있기 때문에 getter를 지양해야 하는 것이었습니다. getter를 무조건 쓰지 않는 것이 아니라 비즈니스 로직을 만들기 위해서
getter로 부터 값을 가져와서 비즈니스 로직을 구현하는 것이 문제였습니다.
객체는 상태(데이터)와 행동(메서드)을 함께 가진 독립적인 실체이기 때문에 단순한 데이터 컨테이너가 되면 안 되는 것입니다.

### 3. Config를 쓰게 된 과정
처음에는 Controller에서 직접 의존성을 받았지만, 계층이 복잡해지면 Controller에서 관리하기 힘들 것 같아서 Config 패턴을 도입하게 되었습니다.

Config를 쓰게 되면서 모든 객체의 생성과 의존성 연결 로직을 한 곳에서 볼 수 있어서 구조를 한 눈에 파악할 수 있었습니다.
새로운 의존성이 추가될 때도 Config 클래스만 수정하면 되므로 유지보수가 쉬워질 것 같았습니다.
만약에 Config 클래스가 없었더라면 Controller에서 `this.inputView = new InputView();` 이런식으로 직접 생성하는 방식으로 구현해야 됐습니다.
위 방식으로 하게 된다면 중복 생성 가능성이 높아져 같은 객체를 공유하지도 못하고 결합도가 증가하는 문제가 발생할 수도 있어 수정하게 되었습니다.
